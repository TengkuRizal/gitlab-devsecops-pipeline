# Alert Response Runbook

## Overview

This runbook documents the response process for alerts generated by the homelab DevSecOps/SRE monitoring stack.

The initial alert covered by this runbook is:

```text
DemoNginxDeploymentUnavailable
```

This alert is generated by Prometheus and surfaced through Alertmanager when the `demo-nginx` deployment has fewer than the expected number of available replicas.

The purpose of this runbook is to provide a repeatable operational response process for alert validation, impact assessment, GitOps state verification, workload restoration, evidence capture, and post-incident review.

---

## Alert Scope

| Alert | Description |
|---|---|
| `DemoNginxDeploymentUnavailable` | Fires when `demo-nginx` has fewer than 3 available replicas for more than 1 minute |

---

## Environment Reference

| Component | Role |
|---|---|
| Kubernetes | Runtime platform for workloads |
| Prometheus | Evaluates alert rules |
| PrometheusRule | Defines alert conditions |
| Alertmanager | Displays and routes alerts |
| kube-state-metrics | Exposes Kubernetes object state metrics |
| ArgoCD | GitOps controller and desired-state reconciler |
| GitHub Repository | Source of truth for manifests and evidence |
| `demo` namespace | Namespace for `demo-nginx` workload |
| `monitoring` namespace | Namespace for Prometheus, Grafana, and Alertmanager |

## Alert Rule Definition

Alert name:

```text
DemoNginxDeploymentUnavailable
```

PromQL expression:

```promql
kube_deployment_status_replicas_available{namespace="demo", deployment="demo-nginx"} < 3
```

Alert duration:

```text
for: 1m
```

Meaning:

```text
The demo-nginx deployment has fewer than 3 available replicas for more than 1 minute.
```

Severity:

```text
warning
```

## Initial Response Checklist

When the alert fires, perform the following:

- [ ] Confirm alert is active in Alertmanager.
- [ ] Confirm affected namespace and deployment.
- [ ] Check current Kubernetes deployment state.
- [ ] Check pod status and recent events.
- [ ] Check ArgoCD sync and health status.
- [ ] Confirm whether the alert was caused by intentional testing or real degradation.
- [ ] Restore workload to expected state if required.
- [ ] Confirm alert resolves.
- [ ] Capture evidence.
- [ ] Document incident or test result.

## Step 1: Confirm Alert in Alertmanager

Access Alertmanager UI.

Example NodePort access:

```text
http://NODE_IP:ALERTMANAGER_NODEPORT
```

Confirm the alert:

```text
DemoNginxDeploymentUnavailable
```

Expected alert labels:

```text
alertname="DemoNginxDeploymentUnavailable"
namespace="demo"
deployment="demo-nginx"
severity="warning"
service="demo-nginx"
environment="homelab"
```

---

## Step 2: Confirm Alert from Kubernetes CLI

Check Alertmanager service:

```bash
kubectl get svc monitoring-kube-prometheus-alertmanager -n monitoring
```

Check PrometheusRule:

```bash
kubectl get prometheusrule demo-nginx-availability-alerts -n monitoring
kubectl describe prometheusrule demo-nginx-availability-alerts -n monitoring
```

Check monitoring pods:

```bash
kubectl get pods -n monitoring -o wide
```

---

## Step 3: Validate Deployment Impact

Check `demo-nginx` deployment:

```bash
kubectl get deployment demo-nginx -n demo -o wide
```

Expected healthy state:

```text
demo-nginx   3/3   3   3
```

If the alert is firing, the deployment may show fewer than 3 available replicas.

Check pods:

```bash
kubectl get pods -n demo -o wide
```

Check events:

```bash
kubectl get events -n demo --sort-by=.metadata.creationTimestamp | tail -30
```

Describe deployment:

```bash
kubectl describe deployment demo-nginx -n demo
```

---

## Step 4: Check ArgoCD State

Check ArgoCD Application:

```bash
kubectl get application demo-nginx -n argocd
```

Expected healthy GitOps state:

```text
demo-nginx   Synced   Healthy
```

Describe application:

```bash
kubectl describe application demo-nginx -n argocd
```

Check full state:

```bash
kubectl get application demo-nginx -n argocd -o yaml
```

Key fields:

```text
status.sync.status
status.health.status
status.operationState.phase
status.operationState.message
```

## Step 5: Determine Cause

Common causes for this alert:

| Cause | How to Identify |
|---|---|
| Intentional test | Recent planned Phase 3 alert test or controlled replica reduction |
| Manual drift | Deployment scaled manually using `kubectl scale` |
| Git desired state changed | `kubernetes/deployment.yaml` replica count changed in Git |
| Pod failure | Pods show `CrashLoopBackOff`, `ImagePullBackOff`, or not ready |
| Node issue | Pods stuck pending or node unavailable |
| Resource pressure | Pods evicted, pending, or OOMKilled |
| ArgoCD sync issue | Application `OutOfSync`, `Degraded`, or `Unknown` |
| Image pull issue | Pod events show image pull failure |
| Readiness failure | Pods running but not ready |

## Step 6: Restore Desired State

### Method 1: Restore Through GitOps

If the Git desired state is wrong, fix the manifest in Git.

On Mac repo:

```bash
cd ~/TengkuRizal

grep -n "replicas:" kubernetes/deployment.yaml
```

Set replicas back to expected value:

```yaml
replicas: 3
```

Commit and push:

```bash
git add kubernetes/deployment.yaml
git commit -m "Restore demo-nginx replicas after alert"
git pull --rebase origin main
git push origin main
```

Refresh ArgoCD:

```bash
kubectl annotate application demo-nginx -n argocd \
  argocd.argoproj.io/refresh=hard \
  --overwrite
```

Validate:

```bash
kubectl get application demo-nginx -n argocd
kubectl get deployment demo-nginx -n demo
kubectl get pods -n demo -o wide
```

Expected:

```text
demo-nginx   Synced   Healthy
demo-nginx   3/3
```

---

### Method 2: Emergency Manual Restore

Use this only if immediate restoration is required and GitOps behavior is understood.

```bash
kubectl scale deployment demo-nginx -n demo --replicas=3
```

Then validate:

```bash
kubectl get deployment demo-nginx -n demo
kubectl get pods -n demo -o wide
```

Important:

If ArgoCD self-heal is enabled and Git desired state still says a different replica count, ArgoCD may revert the manual change.

After emergency manual restoration, update Git so desired state matches the recovered state.

---

## Step 7: Confirm Alert Resolution

Wait for Prometheus and Alertmanager to evaluate the restored state.

Check deployment:

```bash
kubectl get deployment demo-nginx -n demo
```

Expected:

```text
demo-nginx   3/3   3   3
```

Check ArgoCD:

```bash
kubectl get application demo-nginx -n argocd
```

Expected:

```text
demo-nginx   Synced   Healthy
```

Check Alertmanager UI and confirm the alert no longer appears as active.

## Step 8: Capture Evidence

Capture evidence from `k8master`:

```bash
mkdir -p ~/phase-3-evidence

kubectl get prometheusrule demo-nginx-availability-alerts -n monitoring -o yaml > ~/phase-3-evidence/demo-nginx-prometheus-rule.yaml
kubectl get deployment demo-nginx -n demo -o wide > ~/phase-3-evidence/demo-nginx-alert-response-deployment.txt
kubectl get pods -n demo -o wide > ~/phase-3-evidence/demo-nginx-alert-response-pods.txt
kubectl get application demo-nginx -n argocd > ~/phase-3-evidence/demo-nginx-alert-response-argocd-app.txt
kubectl get pods -n monitoring -o wide > ~/phase-3-evidence/monitoring-pods.txt
kubectl get alertmanager -n monitoring > ~/phase-3-evidence/alertmanager-status.txt
kubectl get prometheus -n monitoring > ~/phase-3-evidence/prometheus-status.txt
```

Archive:

```bash
tar -czf ~/phase-3-alert-response-evidence.tar.gz -C ~ phase-3-evidence
```

Copy to Mac repo:

```bash
cd ~/TengkuRizal

mkdir -p evidence/phase-3

scp k8@10.10.1.70:/home/k8/phase-3-alert-response-evidence.tar.gz /tmp/phase-3-alert-response-evidence.tar.gz
tar -xzf /tmp/phase-3-alert-response-evidence.tar.gz -C /tmp
cp /tmp/phase-3-evidence/* evidence/phase-3/
```

Commit:

```bash
git add evidence/phase-3/
git commit -m "Add alert response evidence"
git pull --rebase origin main
git push origin main
```

## Common Troubleshooting Scenarios

### Alert Fires But Deployment Looks Healthy

Possible causes:

- Prometheus has not evaluated resolved state yet
- Metric delay
- Alertmanager still displaying recently firing alert
- Alert is grouped with stale state
- Browser UI not refreshed

Check:

```bash
kubectl get deployment demo-nginx -n demo
kubectl get pods -n demo -o wide
```

Wait a few minutes and refresh Alertmanager.

---

### Alert Does Not Fire

Possible causes:

- PrometheusRule label does not match Prometheus selector
- Rule has not been loaded
- Query does not return metric
- `for` duration has not elapsed
- kube-state-metrics is not running

Check:

```bash
kubectl get prometheusrule demo-nginx-availability-alerts -n monitoring
kubectl describe prometheusrule demo-nginx-availability-alerts -n monitoring
kubectl get pods -n monitoring
```

---

### Alertmanager UI Not Accessible

Possible causes:

- Alertmanager service is ClusterIP
- Wrong NodePort
- Wrong node IP
- Firewall or routing issue

Check:

```bash
kubectl get svc monitoring-kube-prometheus-alertmanager -n monitoring
curl -I http://NODE_IP:NODEPORT
```

---

### ArgoCD Does Not Restore Desired State

Possible causes:

- Self-heal disabled
- Application not synced
- Git desired state is wrong
- ArgoCD controller issue
- Manifest error
- Resource conflict

Check:

```bash
kubectl get application demo-nginx -n argocd
kubectl describe application demo-nginx -n argocd
kubectl logs -n argocd statefulset/argocd-application-controller --tail=100
```

## Success Criteria

Alert response is successful when:

- Alert was confirmed.
- Impact was assessed.
- Root cause or likely cause was identified.
- Workload was restored to expected state.
- ArgoCD Application returned to `Synced` and `Healthy`.
- Deployment returned to `3/3`.
- Alert resolved or is expected to resolve.
- Evidence was captured.
- Documentation was updated if needed.
